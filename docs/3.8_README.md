# Step 3.8 - Holder Distribution Filter

## Overview

The Holder Distribution Filter (Step 3.8) analyzes token holder concentration and distribution patterns to identify potentially risky or manipulated tokens. It examines the top holders, detects team-related wallets, identifies new wallets, and calculates various concentration metrics.

## Purpose

- **Concentration Analysis**: Detect tokens with excessive concentration in top holders
- **Team Detection**: Identify team-related wallets and calculate their combined holdings
- **New Wallet Detection**: Flag tokens with suspicious new wallet activity
- **Risk Assessment**: Provide comprehensive holder distribution risk scoring

## Configuration

All configuration is managed through environment variables in `.env`:

```env
# Step 3.8 - Holder Distribution Filter
HOLDERS_ENABLED=true                    # Enable/disable the filter
HOLDERS_CRITICAL=true                   # Make filter critical (blocks on fail)
HOLDERS_MODE=LOG_ONLY                   # LOG_ONLY | STRICT
HOLDERS_CACHE_TTL_MS=60000             # Cache TTL (60 seconds)
HOLDERS_RPC_TIMEOUT_MS=2500            # RPC call timeout
HOLDERS_CONCURRENCY=4                   # Max concurrent RPC calls
HOLDERS_RATE_LIMIT_QPS=10              # Rate limit (queries per second)
HOLDERS_TOP_N=20                       # Number of top accounts to analyze
HOLDERS_TOP1_MAX_PCT=5                 # Max top-1 holder percentage
HOLDERS_TOP5_MAX_PCT=10                # Max top-5 holders percentage
HOLDERS_TOP10_MAX_PCT=20               # Max top-10 holders percentage
HOLDERS_TEAM_MAX_PCT=15                # Max team holdings percentage
HOLDERS_NEW_WALLETS_WARN_PCT=40        # New wallets warning threshold
HOLDERS_NEW_WALLETS_FAIL_PCT=60        # New wallets failure threshold
HOLDERS_NEW_WALLET_AGE_DAYS=7          # Definition of "new" wallet (days)
HOLDERS_VERIFY_TX_HISTORY=true         # Enable transaction history verification
```

## Algorithm

### 1. Input Validation
- Validates mint address format
- Checks cache for existing results
- Retrieves token supply information

### 2. Holder Analysis
- Fetches top N token accounts using `getTokenLargestAccounts`
- Retrieves account info for each holder using `getParsedAccountInfo`
- Excludes known contracts (LP pools, burn addresses, system programs)
- Calculates percentage holdings for each account

### 3. Team Wallet Detection
- Checks if owner matches `updateAuthority` from metadata
- Verifies against `creators` list in metadata
- Optionally analyzes transaction history for early participation
- Flags wallets involved in initial token distribution

### 4. New Wallet Detection
- Retrieves transaction history using `getSignaturesForAddress`
- Calculates wallet age from first transaction
- Flags wallets younger than `HOLDERS_NEW_WALLET_AGE_DAYS`

### 5. Metrics Calculation
- **top1_pct**: Percentage held by largest holder
- **top5_pct**: Combined percentage of top 5 holders
- **top10_pct**: Combined percentage of top 10 holders
- **team_pct**: Combined percentage of team-related wallets
- **new_wallets_pct**: Combined percentage of new wallets
- **num_unique_owners**: Total number of unique holders

### 6. Decision Logic
```javascript
if (top1_pct > TOP1_MAX) → fail (top1_concentration)
else if (top5_pct > TOP5_MAX) → fail (top5_concentration)
else if (top10_pct > TOP10_MAX) → warn/fail (top10_high)
else if (team_pct > TEAM_MAX) → fail (team_centralization)
else if (new_wallets_pct > NEW_FAIL) → fail (new_wallets_mass)
else if (new_wallets_pct > NEW_WARN) → warn (new_wallets_suspicious)
else if (num_unique_owners < 3) → warn (too_few_owners)
else → pass
```

## Operating Modes

### LOG_ONLY Mode
- Analyzes and logs all holder distribution data
- Never blocks tokens (always returns `pass: true`)
- Sets `action: "passed_log_only"` for failed cases
- Ideal for initial deployment and data collection

### STRICT Mode
- Enforces all thresholds strictly
- Blocks tokens that fail concentration checks
- Returns `pass: false` for violations
- Used in production after threshold tuning

## Performance Features

### Caching System
- 60-second TTL cache for holder analysis results
- Cache key format: `holders:{mint}|{TOP_N}`
- Reduces redundant RPC calls for recently analyzed tokens

### Rate Limiting
- 10 QPS limit with 4 concurrent requests
- Prevents RPC overload and API rate limiting
- Automatic request queuing and backoff

### Error Handling
- Retry logic for transient RPC failures
- Timeout protection for slow responses
- Graceful degradation on analysis errors

## Integration

### Pipeline Position
Step 3.8 runs after Step 3.7 (Pool Size) and before Step 3.9 (Quality) in the filter pipeline.

### Dependencies
- **Helius RPC**: For `getTokenLargestAccounts`, `getParsedAccountInfo`, `getSignaturesForAddress`
- **Metadata**: From Step 3.4 for team wallet detection
- **Known Contracts**: From Steps 3.6/3.7 for exclusion lists

## Deployment Strategy

### Stage 1: Development (24-48 hours)
- `HOLDERS_MODE=LOG_ONLY`
- `HOLDERS_CRITICAL=false`
- Collect baseline metrics and tune thresholds

### Stage 2: Canary (24 hours)
- `HOLDERS_MODE=STRICT`
- `HOLDERS_CRITICAL=false`
- Monitor for false positives

### Stage 3: Production
- `HOLDERS_MODE=STRICT`
- `HOLDERS_CRITICAL=true`
- Full enforcement of holder distribution rules

## Troubleshooting

### Common Issues
1. **High RPC Errors**: Increase timeout or reduce concurrency
2. **Low Cache Hit Rate**: Check TTL settings and token diversity
3. **Slow Processing**: Optimize RPC calls or increase concurrency
4. **False Positives**: Adjust thresholds based on real data

### Debug Logging
Set `LOG_LEVEL=debug` to enable detailed processing logs including:
- Individual holder analysis
- Team wallet detection logic
- Cache hit/miss details
- RPC call timing and errors

## Threshold Recommendations

Based on Solana token analysis, recommended starting thresholds:

- **top1_max**: 5% (prevents single-holder dominance)
- **top5_max**: 10% (ensures reasonable distribution)
- **top10_max**: 20% (allows for some concentration)
- **team_max**: 15% (reasonable team allocation)
- **new_wallets_warn**: 40% (suspicious new activity)
- **new_wallets_fail**: 60% (likely manipulation)

These should be adjusted based on real-world data and false positive rates.
